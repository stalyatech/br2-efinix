# efx — Ti375C529 (ti375_oob) Linux build driver

`efx` wraps this repo's `init.sh` and the Buildroot targets behind one repeatable
command, and puts a browser front end on top of it.

```
tools/efx/efx preflight            # check the host
tools/efx/efx config detect --write
tools/efx/efx config configure     # clone Buildroot, generate the device tree
tools/efx/efx fsbl build           # first-stage bootloader
tools/efx/efx opensbi build
tools/efx/efx uboot build
tools/efx/efx kernel build
tools/efx/efx image build
tools/efx/efx gui                  # http://127.0.0.1:8760
```

Everything the GUI does is one of these commands, so any button can be
reproduced — and debugged — in a shell.

---

## Why this exists

`init.sh` is built to be sourced once, interactively, into a pristine tree. It
writes into tracked files, appends to them without guards, needs a TTY, and
fails outright if the build directory already exists. On top of that, this
project's hardware differs from the Efinix reference designs in ways that make
`init.sh`'s built-in assumptions wrong.

`efx` does not replace `init.sh` — it drives it, and fixes up what it gets wrong:

| Problem | What efx does |
|---|---|
| `init.sh` rewrites tracked files and appends to them on every run | Restores each one from git first, so configuring twice yields an identical tree |
| `-u`/`-e` inject an AXI map that collides with this SoC's own peripherals at `0xE801_0000`–`0xE805_0000` | Never passes `-u`/`-e`; injects `socmap/ti375_oob_hard.h` instead |
| The project's `soc.h` has CRLF endings, so `init.sh`'s `[[ $ext_c == 1 ]]` never matches and RVC silently drops out of the kernel config | Normalises the staged copy to LF |
| `uboot_32_defconfig` hard-codes `CONFIG_DEBUG_UART_BASE=0xF8010000`, which is the *soft* SoC's UART | Generates the real value from `soc.h` into `state/uboot_derived.cfg` |
| `init.sh:567` tests a literal `$(BR2_EXTERNAL_EFINIX_PATH)/…` string with `-f`, so the board's U-Boot fragment is never applied | Appends the fragments to the generated defconfig directly |
| `init.sh:859` reads `[ "$KERNEL_SELECTION" ! = "2" ]` — a space after `!` — so `-k 2` errors out | Rejects kernel 5.10 up front instead of failing halfway |
| `mkdir $BUILD_DIR` without `-p` | Uses `reconfigure`/`regen-dt`, or `--force` to start over |
| The project's `soc.h` is modified in place | Staged to `state/soc.h`; the project copy is never touched |
| The device tree generator's peripheral bindings only come from the `-u`/`-e` override directories | Installs project overrides from `dtoverlay/` into the board directory the generator checks anyway |
| U-Boot builds `mkeficapsule`, which needs GnuTLS headers, on a board with no EFI | `CONFIG_TOOLS_MKEFICAPSULE` off in `overlays/uboot_ti375_oob.cfg` |

The project itself is never modified except where it must be: the FSBL build
swaps in br2-efinix's `bootloaderConfig.h` (the original is kept and restorable
with `efx fsbl restore`).

## Configuration

`tools/efx/efx.conf`, generated by `efx config detect --write`. The schema —
types, defaults and the descriptions the GUI shows — is `tools/efx/efx.keys`.

The keys that matter most:

- **`SOC_VARIANT`** — `hard` (the 1 GHz quad-core hardened block) or `fcu` (the
  soft Sapphire SoC). Selects which `soc.h` drives the whole build.
- **`FSBL_HOST`** — which SoC's BSP the bootloader is built for. See below.
- **`ROOTFS_MODE`** — `initramfs` builds the rootfs into the kernel image;
  `sdcard` produces `sdcard.img` via genimage.
- **`SOCMAP_OVERLAY`** — the project-specific AXI map appended to the staged
  `soc.h`.
- **`EFX_DL_DIR` / `EFX_CCACHE_DIR`** — relocate Buildroot's caches, which
  otherwise land in `$HOME` and grow to tens of gigabytes.

## Which SoC runs Linux

This design has two RISC-V SoCs, and the peripherals Linux needs are not all on
the one you might expect. In the current bitstream:

| Resource | Owner | Evidence |
|---|---|---|
| SD host (gSDHC) CSRs | soft FCU SoC | `ti375_oob_top.v:469`, `:520-522` |
| Ethernet (gTSE) CSRs | soft FCU SoC | same AXI switch |
| SPI boot flash pins | soft FCU SoC | `ti375_oob_top.v:1592` |
| `sd_int`, DMA interrupts | FCU PLIC (user F/G/H = 21/22/23) | `:665`, `:807-808` |
| DDR | shared — both reach the LPDDR4x controller | `gAXIM_5to1_switch` |

With `SOC_VARIANT=hard`, Linux boots on the hardened SoC over UART and DDR, but
the SD host, Ethernet and SPI flash are unreachable until the RTL routes those
CSRs into the hard SoC's AXI-A window. That is why `ROOTFS_MODE=initramfs` is the
default: there is currently nothing to load a root filesystem *from*.

`socmap/ti375_oob_hard.h` holds the addresses the RTL is expected to use. Change
them there and in the RTL together, then run `efx config regen-dt`.

## Getting the FSBL into the FPGA

The bootloader runs from on-chip RAM, so the bitstream has to carry it. How that
works depends on `FSBL_HOST`, and the two paths differ by orders of magnitude:

- **`FSBL_HOST=hard`** — the hardened SoC's 16 KiB on-chip RAM is loaded from
  `OCR_FILE_PATH` in `<project>.peri.xml` (`sw/boot/bootloader.hex`)
  by the Interface Designer, so a new FSBL takes an `efx fpga build`.
  `efx fpga verify-fsbl` checks, bit for bit, which FSBL a built bitstream
  carries.
- **`FSBL_HOST=fcu`** — the soft SoC's RAM is fabric BRAM.
  `efx fpga bram-update` rewrites it inside the finished bitstream. Seconds.
  With `FSBL_HOST=hard` the same verb patches the FCU's own firmware
  (`FCU_FIRMWARE`) instead.

The FSBL is built with the native Linux toolchain rather than the Efinity RISC-V
IDE, which is installed here as Windows binaries only. `-march`/`-mabi` come from
`soc.h`, with `_zicsr_zifencei` written out explicitly: GCC 12+ stopped implying
`zifencei`, and the BSP uses `fence.i`.

Because that is not the toolchain the vendor tested, `efx fsbl build` hard-fails
if the image does not fit `SYSTEM_RAM_A_SIZE`, and checks the ELF class, ABI and
entry point. An FSBL that overflows on-chip RAM does not report an error on
hardware — it just does not boot.

## The web interface

```
tools/efx/efx gui [--port 8760]
```

Left-hand navigation: Dashboard, Configuration, FSBL, OpenSBI, U-Boot, Kernel,
Rootfs & Image, FPGA/Bitstream, Flash, Logs, Settings. Each component page has a
settings panel, Build/Rebuild/Clean actions, a live log and an artifact table.

Notes on what it deliberately will not do:

- **`menuconfig` is not available.** It is a terminal program. The Kernel and
  U-Boot pages edit the *fragment files* that feed the build instead — the real
  source of truth, and unlike a `.config` edit they survive a reconfigure. The
  page also prints the `make …-menuconfig` command to run in a terminal.
- **Flashing is CLI-only.** The Flash page lists devices and shows the commands;
  choosing a block device to overwrite is not a mouse gesture. `efx flash sdcard`
  refuses non-removable devices, refuses partitions, refuses mounted disks, and
  requires the device's model and size typed back.

Because the server executes build commands, it binds to loopback only, refuses
cross-origin requests, and accepts only whitelisted component/verb pairs — never
a path or command line from the browser.

One job runs at a time. The GUI and the CLI share the same `flock`, so a build
started in a terminal blocks the GUI and vice versa.

## What each step produces

| Step | Artifacts |
|---|---|
| `config configure` | `.config`, `linux.dts`, `uboot.dts` |
| `fsbl build` | `sw/boot/bootloader.{elf,bin,hex}` in the Efinity project |
| `opensbi build` | `images/fw_jump.bin` |
| `uboot build` | `images/u-boot.bin` |
| `kernel build` | `images/vmlinux`, `images/linux.dtb` |
| `image build` | `images/Image`, `images/uImage`, `images/rootfs.tar`, and `sdcard.img` in `sdcard` mode |

`Image` and `uImage` belong to the image step, not the kernel step:
`boards/efinix/common/post_build.sh` makes them, and Buildroot runs that during
target-finalize — which a `linux-rebuild` never reaches.

`opensbi` and `uboot` builds also check their output against the flash slot the
FSBL will copy from (`OPENSBI_SIZE`, `UBOOT_SIZE` in
`boards/efinix/common/bootloaderConfig.h`). Overrunning a slot gives a silently
truncated copy at boot, so the build fails instead.

### `sdcard.img` needs mtools

In `ROOTFS_MODE=sdcard`, genimage shells out to `mcopy` to fill the FAT boot
partition. If `mcopy` is missing the Buildroot build still exits 0 — it just
never writes `sdcard.img` — so `efx image build` checks for the file itself and
fails loudly. `preflight` reports it too (as a warning in `initramfs` mode, where
it is not needed).

Note that the distribution package is not enough: `docs/known_issues.md` records
that Ubuntu's `mcopy` fails on these images and mtools 4.0.44 has to be built
from source.

## Cleaning

| Level | Effect |
|---|---|
| `efx <component> clean` | `<pkg>-dirclean` — cheapest, use this |
| `efx clean images` | empties `images/` |
| `efx clean build` | Buildroot `make clean` — drops the toolchain too; next build is a first build |
| `efx clean workspace` | deletes the whole workspace including the Buildroot checkout |
| `efx clean repo-reset` | restores the repo files the configuration step rewrote |

## Cancelling

Jobs run in their own process group, so cancelling stops the whole `make` tree.
A cancelled component is marked `cancelled` and refuses to build again until it
is cleaned: a half-written package directory poisons every later build, and that
failure is much harder to diagnose than an explicit refusal.

```
tools/efx/efx cancel
tools/efx/efx kernel clean
```

## Layout

```
tools/efx/
  efx                  dispatcher — the only entry point
  efx.conf             local configuration (git-ignored)
  efx.keys             configuration schema
  socmap/              project-specific soc.h overlays
  overlays/            hand-authored kernel and U-Boot fragments
  lib/                 shared shell helpers
  scripts/             one script per area
  webgui/              stdlib-only HTTP server + vanilla JS front end
  logs/  state/        runtime output (git-ignored)
```

`state/` also keeps backups: `tree-backup-*` (the repo files the configuration
step rewrites), `fsbl-backup/` (the project's original `bootloaderConfig.h` and
`soc.mk`) and `hardsoc-settings.json.bak`.
